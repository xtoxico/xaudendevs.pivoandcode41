Prompting Riguroso

Glosario de términos para la charla: anglicismos, conceptos de IA, arquitectura, TypeScript, testing y desarrollo guiado por especificaciones.

66 términos

Idea central

La IA no debe decidir la arquitectura por nosotros. La IA debe obedecer Specs, contratos, capas y tests. El prompt lanza la tarea; la Spec define la verdad.

“CoT no es pedirle a la IA que piense bonito; es obligarla a dejar por escrito el razonamiento arquitectónico antes de tocar una línea de código.”
VibeCoding

Forma de programar “por sensaciones”, aceptando código generado por IA porque parece correcto, compila o funciona en el caso feliz, sin entender bien sus implicaciones técnicas.

IA generativa

Tipo de inteligencia artificial capaz de generar texto, código, imágenes u otros contenidos a partir de instrucciones en lenguaje natural.

LLM

Siglas de Large Language Model. Modelo de lenguaje grande entrenado para comprender y generar texto. ChatGPT, Gemini, Claude o Copilot se basan en este tipo de tecnología.

Prompt

Instrucción que se le da a una IA para que realice una tarea. En la charla, el prompt no debe ser la fuente de verdad, sino una orden de ejecución.

System Prompt

Instrucción de alto nivel que define cómo debe comportarse la IA. Por ejemplo: no generar código sin leer antes la Spec o no mezclar lógica de negocio con infraestructura.

Prompting Riguroso

Técnica de uso de IA donde no se pide código de forma improvisada, sino que se obliga al modelo a seguir reglas, Specs, contratos, capas y tests.

Spec / Design Spec

Documento de especificación de diseño. Describe qué debe hacer un módulo, qué reglas debe cumplir, qué arquitectura debe respetar y qué restricciones tiene.

Spec Driven Development

Desarrollo guiado por especificaciones. Primero se define la Spec; después la IA genera contratos, tests y código alineado con esa Spec.

Documentación viva

Documentación que vive junto al código y se usa activamente para desarrollar. Si cambia el negocio, se actualiza la Spec y la IA debe obedecerla.

Contrato

Definición formal de cómo se comunican dos partes del sistema. Puede ser una interfaz TypeScript, un esquema JSON, un endpoint OpenAPI o un DTO.

DTO

Siglas de Data Transfer Object. Objeto usado para transportar datos entre capas o entre cliente y servidor. Por ejemplo, RegisterUserRequestDto.

Interface TypeScript

Contrato de TypeScript que define la forma que debe tener un objeto o clase. Ayuda a que la IA no invente estructuras distintas cada vez.

OpenAPI / Swagger

Estándar para documentar y definir APIs REST: rutas, métodos HTTP, parámetros, cuerpos de petición, respuestas y códigos de estado.

JSON Schema

Formato para definir la estructura esperada de un objeto JSON. Sirve para validar datos de entrada y salida.

Zod

Librería de TypeScript para validar datos en tiempo de ejecución y generar tipos seguros.

TypeBox

Librería para definir esquemas de datos compatibles con TypeScript y JSON Schema.

Context Window

Ventana de contexto de una IA. Es la cantidad de información que el modelo puede tener presente en una interacción: prompts, código, documentos, historial, etc.

Context Window Optimization

Técnica de optimizar qué información se entrega a la IA para que no se distraiga ni mezcle conceptos. No consiste en darle todo el repositorio, sino el contexto justo.

Lost in the Middle

Problema por el cual los modelos pueden prestar menos atención a la información situada en medio de contextos muy largos. Por eso más contexto no siempre significa mejor comprensión.

Atomic Specs

Especificaciones pequeñas, separadas y enfocadas. Por ejemplo: una Spec para dominio, otra para contratos API y otra para infraestructura.

Inyección selectiva de contexto

Dar a la IA solo los documentos o archivos que necesita para la tarea actual, evitando ruido innecesario.

CoT / Chain-of-Thought

Técnica que fuerza a la IA a razonar antes de responder. En la charla se aplica a arquitectura: antes de escribir código, debe analizar capas, responsabilidades y trade-offs.

Trade-off

Compromiso entre dos decisiones técnicas. Por ejemplo, simplicidad frente a escalabilidad, rapidez frente a mantenibilidad o abstracción frente a claridad.

Arquitectura Hexagonal

Patrón arquitectónico que separa el núcleo de negocio de los detalles externos como base de datos, APIs o frameworks. También se conoce como Ports and Adapters.

Clean Architecture

Estilo arquitectónico que separa el software en capas, protegiendo el dominio de negocio de frameworks, bases de datos o interfaces externas.

Dominio

Parte del software que representa las reglas esenciales del negocio. Debe ser lo más independiente posible de frameworks y tecnología externa.

Infraestructura

Capa que contiene detalles técnicos: base de datos, servicios externos, frameworks, APIs, correo, filesystem, etc.

Capa de aplicación

Capa que coordina casos de uso. No es exactamente dominio puro ni infraestructura; orquesta acciones del sistema.

Caso de uso

Operación concreta que el sistema debe realizar. Por ejemplo: registrar usuario, iniciar sesión, emitir token o validar email.

Facade / Fachada

Patrón de diseño que ofrece una interfaz simple para acceder a una lógica interna más compleja. En la demo, el controller llama a la facade, y la facade orquesta services y repositories.

Controller

Capa que recibe la petición HTTP, extrae datos y llama a la facade. No debe contener reglas de negocio.

Route

Archivo o capa donde se definen las rutas HTTP, por ejemplo POST /api/auth/register.

Service

Capa donde se implementan operaciones internas o lógica reutilizable del módulo.

Repository

Capa que abstrae el acceso a datos. Permite que el resto de la aplicación no dependa directamente de SQL, ORM o base de datos concreta.

Model

Representación interna de una entidad o estructura de datos del sistema.

Acoplamiento

Grado de dependencia entre partes del sistema. Mucho acoplamiento dificulta modificar una parte sin romper otra.

Cohesión

Grado en que una clase, módulo o función tiene una responsabilidad clara y bien enfocada. Alta cohesión suele ser buena.

Responsabilidad única

Principio según el cual una clase o función debe tener una sola razón para cambiar. Está relacionado con el principio SOLID conocido como SRP.

Código espagueti

Código desordenado, muy acoplado, difícil de seguir y modificar. En la charla aparece como código espagueti de IA: parece limpio, pero esconde caos arquitectónico.

Deuda técnica

Coste futuro generado por decisiones rápidas o pobres en el presente. La IA puede acelerar esa deuda si se usa sin control.

Hiperinflación de código

Expresión para describir cómo la IA puede generar mucho código muy rápido, aumentando deuda técnica y complejidad a gran velocidad.

Happy path

Camino ideal en el que todo funciona correctamente. El problema es validar solo ese caso y olvidar errores, excepciones y límites.

TDD

Siglas de Test-Driven Development. Técnica donde primero se escriben tests y luego el código necesario para hacerlos pasar.

Test en rojo

Estado inicial del TDD: el test falla porque la funcionalidad todavía no está implementada.

Test en verde

Estado en el que los tests pasan correctamente. Indica que el código cumple los criterios definidos por los tests.

Suite de tests

Conjunto de pruebas automáticas que validan el comportamiento del sistema.

Mock

Sustituto simulado de una dependencia real. Por ejemplo, un repositorio falso para probar una facade sin base de datos.

API REST

Estilo de API basado en recursos y métodos HTTP como GET, POST, PUT o DELETE.

Endpoint

Ruta concreta de una API. Por ejemplo: POST /api/auth/register.

HTTP Status Code

Código de respuesta HTTP. Por ejemplo: 200 OK, 201 Created, 400 Bad Request, 404 Not Found o 500 Internal Server Error.

Boilerplate

Código repetitivo necesario para arrancar una estructura o proyecto, pero que no aporta lógica de negocio directa.

Runtime

Momento de ejecución del programa. Algo ocurre en runtime cuando pasa mientras la aplicación está funcionando.

Compile-time

Momento de compilación. TypeScript detecta muchos errores antes de ejecutar el programa.

Validación en tiempo de ejecución

Comprobación de datos mientras el programa corre. Por ejemplo, validar que un email tiene formato correcto cuando llega una petición HTTP.

Tipado estático

Sistema de tipos que permite detectar errores antes de ejecutar el código. TypeScript ofrece tipado estático sobre JavaScript.

ORM

Siglas de Object-Relational Mapping. Herramienta que permite trabajar con base de datos usando objetos o modelos en lugar de SQL directo. Prisma o TypeORM son ejemplos.

Framework

Conjunto de herramientas y convenciones para desarrollar aplicaciones. Express, Angular o Next.js son frameworks o entornos de trabajo.

Express

Framework minimalista de Node.js para construir APIs y aplicaciones web.

TypeScript

Lenguaje basado en JavaScript que añade tipos estáticos. Ayuda a crear código más mantenible y seguro.

Vitest

Framework de testing moderno para proyectos JavaScript/TypeScript.

Supertest

Librería para probar endpoints HTTP en aplicaciones Node.js/Express.

Raíl

Metáfora usada en la charla para referirse a restricciones, contratos y tests que guían a la IA para que no se salga del diseño.

Alucinación

Respuesta inventada o incorrecta de una IA que parece plausible. En código puede traducirse en funciones inexistentes, APIs inventadas o decisiones no especificadas.

Fuente de verdad

Documento, contrato o artefacto que manda sobre los demás. En la presentación, la Spec y los contratos deben ser la fuente de verdad, no el prompt improvisado.

Determinista

Algo que produce resultados previsibles y verificables. En la charla se contrapone a validar código solo porque parece que funciona.

Soberanía técnica

Capacidad del equipo para mantener el control sobre la arquitectura, decisiones técnicas y evolución del software, en lugar de delegarlo ciegamente en la IA.
